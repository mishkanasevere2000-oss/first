# Накопительный импорт — программы 0.4.0–0.9.0, схема 2

Поддерживаются текстовый PDF кредитной карты Сбера (sber_credit_pdf v1)
с 0.6.0 PDF дебетовой карты Сбера (sber_debit_pdf v1),
с 0.7.0 PDF кредитной карты ВТБ (vtb_card_pdf v1),
с 0.8.0 PDF карточного счёта РСХБ (rshb_card_pdf v1),
с 0.9.0 справка о движении средств Т-Банка (tbank_card_pdf v1),
с 0.10.0 выписка счёта Альфа-Банка (alfa_account_pdf v1),
и с 0.5.0 рублёвая справка Ozon Банка (ozon_pdf v1; docs/import_ozon_pdf.md).
Классификация, финансовые итоги, остальные банковские форматы и OCR не добавлены.

## Правила повторов

1. SHA-256 вычисляется по полным байтам файла, а не его имени. Успешно известный
   файл с теми же байтами не добавляет операций даже под другим именем.
2. Для нового файла сопоставляются отдельные события. Реальный уникальный
   банковский transaction ID используется, только если источник его предоставляет.
   Код авторизации Сбера не считается таким ID.
3. Без ID строится SHA-256 стабильных признаков: дата совершения, дата обработки,
   сумма в копейках, направление, описание с нормализованными пробелами, MCC
   при наличии, время МСК либо локальное время и код авторизации при наличии. Банк и счёт задают
   отдельную область идентичности. Регистр описания самовольно не меняется.
4. Остаток, порядок строк, номер страницы, имя файла и период шапки не входят
   в отпечаток. Они не должны превращать старую операцию в новую.
5. Хранится число одинаковых событий: два известных и три в новом источнике
   означают одну новую операцию. Более короткий следующий источник старые
   операции не удаляет. Внутри группы равных признаков точный остаток помогает
   сопоставить конкретную старую запись; при отсутствии такого совпадения
   сохраняется порядок вхождений. Остаток не определяет размер группы.
6. При совпадении настоящего банковского ID, но противоречии основных фактов
   файл отвергается для проверки, а старые записи не перезаписываются.

Это сопоставление банковских записей, а не определение собственных переводов
или возвратов. Расчёты экономического смысла относятся к последующим этапам.
Механизм рассчитан на полные выгрузки поддерживаемого банковского формата за
выбранные дни. Изменения банком устойчивых идентифицирующих полей требуют
отдельного разбора/версии формата; программа не объединяет названия эвристически.

## Хранение и миграция

Схема 2 добавляет:

- operation_identities: операция, банк/счёт, вид ключа, отпечаток, номер вхождения;
- source_files: уникальный SHA-256, первая успешная попытка, число строк,
  метаданные и состояние/пути архивирования;
- import_observations: строки каждого источника, включая повторные, с указанием
  уже существующего либо нового operation_id и исходных наблюдаемых полей;
- archive_status в imports и индекс SHA-256 попыток.

Старые operations, ID, классификации, ручные решения, правила и их версии
не меняются. Миграция 1→2 только создаёт структуру и идентичности старых операций.
Перед ней обязателен проверенный SQLite-backup схемы 1. Сбой откатывает всю
миграцию. Статус старого архива — LEGACY: наличие файла не выдумывается.

Повторная загрузка может содержать другие позиции строк или остатки: старые
банковские факты не обновляются, новые наблюдения сохраняются отдельно.
Наблюдения и идентичности защищены от обычного изменения/удаления триггерами.

## Попытки и ошибки

Подтверждённая попытка получает PENDING, затем SUCCESS или FAILED. Успешная
транзакция целиком включает новые операции/идентичности, все наблюдения,
счётчики, source_files, аудит и статус SUCCESS. Сбой не оставляет частично
успешных финансовых записей; отдельная FAILED-попытка и диагностика сохраняются.

Предпросмотр CLI и отмена не меняют базу. Нечитаемый файл, выбранный через меню,
фиксируется как ошибочная попытка, если база доступна. Файл остаётся на месте.
В журнале достаточно имени файла и указания страницы/строки/причины; полные
банковские данные не выводятся в общедоступные логи.

Перед обработкой следующего подтверждённого файла незавершённые попытки
помечаются прерванными и проверяются ожидающие архивы. Работать следует одним
активным экземпляром программы: совместный многопользовательский запуск
этим этапом не обеспечивается. На обычном старте импорт автоматически не запускается.

## Архивирование и восстановление

SQLite и файловая система не имеют общей транзакции. Используется явный протокол:

1. PDF читается в память; SHA-256 связывает запись с этой неизменной копией.
   Если файл изменился после предпросмотра, подтверждение отвергается.
2. До записи операций создаётся, закрывается, синхронизируется и проверяется
   временная копия в archive/statements/.pending. Её ошибка блокирует импорт.
3. Фиксируется финансовая транзакция; архив получает состояние PENDING.
4. В archive/statements/ГОД/БАНК/SHA256.pdf (sberbank, ozonbank, vtb, rshb, tbank или alfabank) создаётся и проверяется копия.
   Существующий файл с другим содержимым не перезаписывается.
5. После успешной проверки архив отмечается ARCHIVED. Только затем удаляется
   исходный путь, если его байты всё ещё совпадают с SHA-256. Это перенос через
   проверенное копирование, а не безусловное удаление исходника.

При сбое после финансового COMMIT операции уже учтены, но исходный PDF сохраняется,
а состояние архива — ERROR/PENDING. Программа сообщает именно об этом. Повторная
попытка или recover завершает архивирование, не добавляя операций заново.
После отдельного recover исходник может остаться в input; следующий импорт
распознает его как повтор и завершит перенос.

Неизвестный конфликтующий файл архива автоматически не удаляется. Если подтверждённая
временная копия потеряна, повторный импорт тех же байтов позволяет восстановить
её. Файл, изменившийся во время импорта, не удаляется. Временные файлы, оставшиеся
после аварии до финансового COMMIT, могут остаться в .pending: политика их
очистки и хранения относится к эксплуатационному этапу. Не удалять их вслепую.

Архив и его .pending следует переносить вместе с базой при будущих обновлениях.
База не хранит абсолютные пути конкретного компьютера к архивным файлам.

## Команды (из корня проекта)

```powershell
.\.venv\Scripts\python.exe -m program.importers preview "input\выписка.pdf"
.\.venv\Scripts\python.exe -m program.importers import "input\выписка.pdf" --confirm
.\.venv\Scripts\python.exe -m program.importers recover
.\.venv\Scripts\python.exe -m program.database check
.\.venv\Scripts\python.exe -m program.database info
```

Для отдельной базы передать --database. Архив по умолчанию располагается
в archive/statements корня установки; для произвольной базы — рядом с ней
(или на уровень выше, если база лежит в каталоге database).

## Проверенный перенос базы 0.3.0 в новую папку

Сначала закрыть старую программу. В новой папке установить зависимости и запустить
тесты. **Не создавать пустую finance.db до команды copy.**

```powershell
.\.venv\Scripts\python.exe -m program.database copy --source "ПАПКА_СТАРОЙ_ВЕРСИИ\database\finance.db"
.\.venv\Scripts\python.exe -m program.database init
.\.venv\Scripts\python.exe -m program.database check
.\.venv\Scripts\python.exe -m program.database info
```

copy использует SQLite backup API, проверяет результат и не перезаписывает
существующее назначение. Исходная база остаётся нетронутой. init затем обновляет
**копию**, сохранив и проверив отдельный backup исходной схемы. Для старой базы
из этапа 2 полный перенос архива ещё не нужен: там PDF оставался в input.
Исходную папку программы и исходный PDF сохранять отдельно до окончания проверки.

Начиная с ВТБ, при отсутствии operation_time_moscow признак времени берётся
из operation_time_local. Для прежних форматов Сбера признаки и SHA идентичности
не меняются; у Ozon используется банковский ID. Часовой пояс не угадывается.

РСХБ: маска карты, если она есть в отдельной колонке, сохраняется в source_data
и добавляется к признакам идентичности. Отсутствующее поле не меняет прежние
хеши. Отдельные банковские итоги оборотов отсутствуют: в метаданных сохраняется
bank_turnover_totals_present=false, суммы считаются по строкам и не объявляются
сверенными с оборотами банка. Проверяются остатки; пределы контроля полноты
явно показываются до подтверждения и после импорта (docs/import_rshb_pdf.md).

Т-Банк: оба времени сохраняются (operation_time_local и processing_time_local),
часовой пояс не угадывается. Время списания хранится как исходный факт,
в отпечаток операции дополнительно не включается. Начальный/конечный остатки
отсутствуют: NULL в метаданных, не ноль и не вычисленное значение. Итоги
пополнений/списаний сверяются с банком (docs/import_tbank_pdf.md).

Альфа-Банк: код операции не считается уникальным ID. Он сохраняется
в source_data.bank_operation_code и добавляется как именованный элемент
комбинации признаков; прежние хеши без этого поля не меняются. При отсутствии
даты совершения используется дата проводки с явной пометкой POSTING_DATE,
а не утверждение об известной независимой дате покупки (docs/import_alfa_pdf.md).
