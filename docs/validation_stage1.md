## Реально выполненные проверки

Среда разработчика: Linux, Python 3.12.14; sqlite3 из стандартной библиотеки,
pytest 8.4.2, openpyxl 3.1.5.

```sh
.venv/bin/python -m pip install --no-cache-dir -r requirements.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m program.database init
.venv/bin/python -m program.database init
.venv/bin/python -m program.database check
.venv/bin/python -m program.database import-categories --file config/categories.template.xlsx
.venv/bin/python -m program.database import-accounts --file config/own_accounts.template.xlsx
```

pytest: **73 passed**. Перечень проверок включает исходные smoke-тесты, отдельные
процессы командной строки и тесты на временных SQLite/XLSX-файлах.

В текущей среде создана пустая рабочая база: первая команда init сообщает
«База создана. Схема 1»; повторная — «База уже существует и проверена»;
check — «База исправна. Схема 1». Импорт пустых шаблонов: 0 изменений.
Рабочая база не содержит тестовых операций, категорий, правил или счетов.

Проверены успешные и неуспешные случаи:

- Создание, повторное открытие, сохранение данных при повторной инициализации.
- Целые копейки, отрицательный остаток, запрет float в API, неверных направлений,
  обязательных полей, дат и отсутствующих внешних ключей.
- Ручные решения с сохранением истории, неизменность банковской записи,
  защита от автоматической перезаписи и откат при сбое записи аудита.
- Сохранение точной версии правила, запрет дублирования/изменения старых версий.
- Группы из трёх участников, откат группы при несуществующем участнике.
- XLSX: повторный импорт без дублей/лишнего аудита, обновление по ID,
  сохранение отсутствующих в новом файле записей и ссылок старых решений.
- Отказ при циклах, повторных именах/ID, битых родителях, неверных заголовках,
  формулах, неправильных типах и статусах. Ошибка посередине записи откатывает
  и справочник, и аудит.
- Backup перед изменением существующих справочников и блокировка при ошибке backup.
- Миграция 1 и только тестовая миграция 2: успешный переход, проверенный backup,
  повторный запуск, откат таблиц/версии/данных при искусственном сбое.
- Повреждённые, пустые чужие, структурно несовместимые и более новые базы
  не пересоздаются. Нарушенные связи обнаруживаются.
- Импорт модулей и построение меню из отдельной копии программы не создают базу.
- Команда check не создаёт отсутствующий файл; ошибки CLI не выводят traceback
  для проверенных пользовательских ошибок.

`git check-ignore` подтвердил исключение database/finance.db, личных
config/categories.xlsx и own_accounts.xlsx, .venv и backup.

## Что проверит пользователь

1. Скачать обновлённый ZIP из GitHub и распаковать в отдельную новую папку.
2. Создать новую .venv и установить requirements по README.
3. Выполнить pytest: после исправления backup ожидаются 75 прошедших тестов.
4. Дважды выполнить `program.database init`, затем `program.database check`:
   ожидаются создание, распознавание существующей базы и успешная проверка.
5. Запустить BAT: версия 0.2.0, меню и штатный выход. Финансовые пункты пока заглушки.

Пользовательские результаты записываются отдельно после получения, а не заранее.

## Ограничения

Не реализованы банковский импорт, дедупликация, финансовый движок, отчёты,
пользовательские меню базы/справочников, восстановление backup и полный
эксплуатационный цикл этапа 8. Техническая миграция и обязательные backup перед
уже реализованными изменениями работают, но будущие схемы не придуманы заранее.
Поддержка XLSX относится только к справочникам. Критерии MVP A18/A19/A22
подготовлены устройством хранилища, но полностью ещё не закрыты.

## Исправление закрытия SQLite по результатам Windows

Пользователь сообщил: **72 passed, 1 failed**. В test_invalid_backup_removed
возник WinError 32: отклонённая копия не удалялась из-за открытого дескриптора.
Причина в программе, а не в действиях пользователя: контекст sqlite3.Connection
завершает транзакцию, но сам по себе не закрывает соединение.

В migrations.py добавлен contextlib.closing для соединения записи backup и
временной базы проверки схемы. Проверяющее readonly-соединение уже закрывалось
через connect(). Отказ валидатора по-прежнему блокирует дальнейшую работу
с копией; никакие проверки не отключены.

Добавлены два регрессионных сценария с реальными SQLite-соединениями:
успешная и отклонённая копия. Они подтверждают явное закрытие всех созданных
внутри функции соединений и удаление отклонённой копии. На старом коде оба
теста упали даже в Linux; после исправления полный pytest: **75 passed**.
Проверка на Windows исправленной версии ещё не выполнена.
