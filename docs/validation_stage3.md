# Проверки этапа 3 — накопительный импорт

Статус: версия 0.4.0 реализована и проверена в Linux. Пользовательский прогон
Windows ожидается. Схема SQLite — 2. Этап пока не объявлен принятым.

## Изменения

Добавлены processing/deduplication.py, database/imports.py, schema_v2.py и
importers/archive.py. Обновлены миграции, импорт/меню/CLI, операции хранения,
версия, документация и тесты. Новый API copy переносит базу без замены существующего
назначения; info показывает количество операций и состояние попыток.
Дополнительных зависимостей не потребовалось.

Устойчивые признаки и occurrence сохраняют разные одинаковые покупки; SHA-256
распознаёт те же байты независимо от имени файла. Старые банковские факты и
решения не изменяются; новые наблюдения источников хранятся отдельно.

## Выполнено в Linux

Python 3.12.14, текущие pinned requirements.

```sh
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
.venv/bin/python -m program.database init
.venv/bin/python -m program.database check
.venv/bin/python -m program.database info
```

**142 passed**. Ошибок зависимостей нет. Пустая база облачного проекта обновлена
с проверенным backup до схемы 2 и прошла check; info подтвердил отсутствие
операций и попыток. Пользовательская база Windows разработчику не доступна
и этой командой не менялась.

## Что проверяют тесты

- Точный повтор и переименованный источник: новых 0, известны все исходные строки.
- PDF с теми же строками, но другими байтами: новых 0 по сопоставлению операций,
  а не только по хешу файла.
- Настоящее извлечение синтетических PDF-вариантов: короткий (3 строки), полный
  (4), расширенный (5), снова короткий. Приращения: 3, 1, 1, 0. Общее количество — 5.
- Новый одинаковый экземпляр с теми же датами, временем, авторизацией и описанием
  сохраняется отдельно; баланс помогает привязать старую строку к старому ID.
- Разные банк/счёт/даты не схлопываются. При наличии настоящего банковского ID
  действует его приоритет; повтор ID внутри источника и противоречащие факты отвергаются.
- Предпросмотр/отмена не записывают операции; изменившийся после предпросмотра
  файл требует нового подтверждения.
- Ошибки парсинга, валидации и записи оставляют FAILED-историю без частичных
  operations, identities или observations. Неверный PDF остаётся в input.
- Ошибка временного сохранения блокирует запись; ошибка архива после COMMIT
  сохраняет уже учтённые операции, оригинал и явное ERROR-состояние архива.
- Повторная попытка и recover завершают архив без новых операций. Имитированы
  остановка после COMMIT и ситуация «архив готов, состояние ещё PENDING».
- Конфликтующий файл архива не перезаписывается; изменившийся исходник
  не удаляется; пути из базы не могут вывести архивирование за пределы архива.
- Предыдущие временные копии используются при повторе, а не размножаются.
- Прерванная PENDING-попытка помечается FAILED при восстановлении.
- Повреждённые счётчики истории обнаруживаются при проверке базы.
- Реальная схема выпущенной версии 0.3.0 обновляется с сохранением ID,
  банковских фактов, ручной истории, правил и их версий. Тестовая DB создана
  именно кодом тега v0.3.0, исключительно на вымышленных данных.
- Сбой миграции 1→2 откатывает схему/данные и оставляет проверенный backup.
- copy не меняет исходник и не заменяет существующее назначение.
- CLI copy/init/check/info/recover, меню нескольких файлов, предыдущие
  проверки хранилища и поддерживаемого PDF-обработчика проходят.

## Отдельная сверка настоящего источника

Вне публичных тестовых файлов, во временном каталоге:

1. Из тега v0.3.0 извлечён старый код (без создания Git-worktree), им создана
   старая база и импортирован предоставленный пользователем PDF.
2. Новым copy создана проверенная копия; init обновил только её до схемы 2.
3. Первый повтор того же источника распознал все существующие операции,
   не добавив новых, хотя старая база ещё не имела хеша исходного файла.
4. Следующая точная копия распознана уже по SHA-256, также без новых операций.
5. После обновления и обоих импортов исходные ID/поля operations совпали
   с выпущенной старой версией, классификации не добавлялись.
6. Архив совпал по SHA-256, временный входной экземпляр удалялся только после
   проверки архива. Старая база осталась неизменной.
7. Все временные базы удалены. Загруженный пользователем оригинал сохранён.

Персональные суммы, реквизиты, описания, PDF и базы этой проверки не публикуются.
Второй настоящий перекрывающийся источник пока не предоставлен; рост и пересечения
проверены на настоящих PDF-файлах с полностью вымышленными операциями.

## Критерии и ограничения

A1/A2/A20/A21 проверены для единственного поддерживаемого PDF-формата Сбера.
Финальная приёмка всех банков и MVP этим не заменяется. Финансовая классификация,
связи переводов/возвратов, остальные форматы и отчёты не добавлены.

Поддерживается один активный экземпляр приложения. Очистка осиротевших временных
файлов после аварии до COMMIT и полный эксплуатационный интерфейс остаются
последующему этапу. При неизвестном конфликте архива данные сохраняются, а не
исправляются или удаляются автоматически.

## Проверка пользователем на Windows — предстоит

- Отдельная новая папка и .venv, установка зависимостей, pytest: 142 passed.
- Закрыть старую программу; перенести её базу командой copy **до init**.
  Проверить, что исходная старая папка и база сохранились.
- init: миграция с проверенным backup; check: схема 2; info: исходное количество
  операций. Пустую базу вместо старой не создавать.
- Скопировать прежний PDF в новую input. Меню 1, предварительный просмотр, ДА:
  новых 0, известны все ранее загруженные строки; PDF находится в архиве.
- Снова скопировать тот же оригинал в input и подтвердить: новых 0, общий
  счётчик операций по info не изменился; check проходит.
- По возможности проверить более длинную/перекрывающуюся выписку того же
  банковского формата; добавиться должны только действительно новые строки.

Фактические результаты Windows будут записаны после получения от пользователя.
