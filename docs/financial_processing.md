# Финансовый разбор 0.11.0

Пункт 6 меню открывает контроль базы и предварительный финансовый разбор.
Вариант 2 обрабатывает новые решения и изменившиеся подтверждённые связи.
Вариант 3 явно пересчитывает историю за выбранный период. Пустые границы означают
всю историю. До слова ДА база не меняется. Перед записью создаётся проверенный
backup; операция атомарна. Пункт 1 проверяет целостность базы.

Без личных правил и подтверждённых связей операции остаются undefined.
Знак банковской суммы сам по себе не определяет доход или расход. Поэтому
сохранённые 564 операции ещё не означают готовый финансовый отчёт.
Предварительный ERROR при неопределённых типах означает неполноту финансового
разбора; это отдельный показатель от проверки исправности SQLite.

## Приоритет и связи

Последнее ручное решение защищено от автоматики и пересчёта истории. Затем
применяются подтверждённые OWN_TRANSFER/REFUND/CHAIN. Сохранённые решения остаются
при обычной обработке; для новых правил над старой историей нужен явный пересчёт.
Оставшиеся операции проверяются пользовательскими правилами по числовому
приоритету. Разные результаты при равном приоритете дают undefined; одинаковые
результаты выбираются детерминированно с сохранением ID и версии правила.
Технические, возвратные, доходные, специальные и общие правила задаются данными;
ключевых слов банков и личных категорий в движке нет.

Собственные счета берутся только из ACTIVE-справочника. Дата и равная сумма
создают PROPOSED, но не исключают деньги из отчёта. Автоматическое подтверждение
требует дополнительно единственного общего квалифицированного transfer_reference
(пространство_имён:идентификатор), двух собственных разных счетов и равных сумм.
Текущие парсеры такой межбанковский идентификатор не предоставляют: по имеющимся
PDF автоматическое подтверждение собственных переводов не обещается.
Отклонённая пара повторно не предлагается. Противоречивые подтверждённые группы
требуют проверки. В CHAIN технические ноги отделяются от конечной покупки.

В REFUND одна исходная покупка и один или несколько возвратов; сумма возвратов
не больше покупки. Вычет относится к дате каждого возврата и категории исходной
покупки. Например, июльская покупка 100 и августовский возврат 30 дают расходы
июля 100, августа −30, всего 70. Если исходная покупка вручную исключена,
возврат не создаёт вычет. Неподтверждённый возврат не считается доходом.
Правило с original_operation_id создаёт предложение связи, требующее подтверждения.

Расход без категории сохраняется в итогах и попадает в виртуальную группу
«Неклассифицированные расходы». Физическая категория при этом не создаётся.
Тип undefined, неподтверждённые возвраты и противоречивые связи делают суммы
неполными (ERROR). Отсутствие категории, предложенные связи и дата проводки
вместо даты совершения требуют проверки (WARNING). Это предварительный контроль,
не независимый QA и не разрешение на выпуск Excel.

## Правила и служебные команды

Дружелюбные диалоги правил, подтверждения связей и ручного разбора относятся к
этапу 6. На этапе 5 есть строгий JSON-интерфейс для разработчика. Пустой шаблон:
rules/classification_rules.template.json. Личные JSON в rules исключены из Git.
Правило содержит ровно id, name, version, conditions, action, priority,
effective_from (YYYY-MM-DD), status (ACTIVE/DISABLED). Версии последовательны
и неизменны; повтор точной версии ничего не меняет. Активация/смена версии
сама не пересчитывает классификации. Выбирается последняя доступная версия на
дату --as-of; дата операции задаёт отчётный период, а не дату активации правил.

Условие: {"field":"description","op":"contains","value":"TEST"}.
Группы: {"and":[условия]} или {"or":[условия]}, глубина до 8.
Поля: bank, account_id, card_number_mask, description, mcc, counterparty, phone,
bank_operation_type, operation_date, processing_date, amount_kopecks, direction,
has_link, link_type. Недостающие в PDF факты не выдумываются.
Операторы: eq, ne, contains, not_contains, starts_with, ends_with, gt, lt,
between, date_between; допустимость зависит от типа поля. Деньги — целые копейки.
Текст сравнивается после NFKC/casefold; case_sensitive=true отключает casefold.
Для отсутствующего факта допустимы явные eq/ne null; остальные сравнения не
совпадают. Нет eval, regex и исполнения Python из пользовательских данных.
Техническое исключение не допускается правилом только по сумме/дате/направлению.

Действие: operation_type (expense/income/technical/refund/undefined), необязательные
include_in_report, category_id, subcategory_id, project_id, original_operation_id,
comment. Категории и проекты проверяются по активным справочникам. Идентификатор
покупки допускается только для возврата. Technical/undefined не включаются в итог.

```powershell
.\.venv\Scripts\python.exe -m program.processing import-rules --file rules\classification_rules.json
.\.venv\Scripts\python.exe -m program.processing import-rules --file rules\classification_rules.json --confirm
.\.venv\Scripts\python.exe -m program.processing preview --history --start 2026-08-01 --end 2026-08-31 --plan output\preview.json
.\.venv\Scripts\python.exe -m program.processing apply --plan output\preview.json --confirm
.\.venv\Scripts\python.exe -m program.processing status
```

output должна существовать; файл плана не перезаписывается. План содержит данные
операций/решений: хранить локально. Можно передать --database. При изменении базы,
правил или плана после просмотра применение отклоняется, нужен новый просмотр.
Повтор без изменений не создаёт новых решений, аудита или backup.
Обычный запуск и импорт PDF не запускают финансовый пересчёт автоматически.
