# Задание №1 — SQLite и модель данных

Статус: реализовано в программе 0.2.0; проверки Linux выполнены. Проверки
этого этапа на Windows ожидаются; этап ещё не объявлен принятым.
Протокол: `docs/validation_stage1.md`.

## Простыми словами

Создать постоянную «память» программы: один локальный файл `database/finance.db`.
Он будет хранить банковские операции отдельно от решений пользователя.
На этом этапе проверяем устройство хранилища на искусственных данных.
Настоящие выписки, автоматические категории и финансовые отчёты пока не подключаем.

- «ТЗ_Финансовый_анализатор_v1.1_MVP.docx»: разделы 3, 8–11 и критерии A18, A19, A22.
- «Архитектура_Финансового_анализатора_v1.0.docx»: блок 2 и требования к миграциям.

## 1. Создание, подключение и проверка базы

- Реализовать единую точку подключения в `program/database/connection.py`.
- Путь по умолчанию строить относительно корня проекта; в тестах передавать
  отдельный путь внутри временного каталога.
- Явная команда инициализации создаёт новую базу со схемой. Импорт Python-модуля
  и показ основного меню не должны создавать или менять finance.db.
- Повторная инициализация существующей совместимой базы не стирает данные.
- Включать и проверять внешние ключи для каждого подключения SQLite.
- Многошаговые изменения выполнять одной транзакцией; ошибка откатывает всё действие.
- Проверять структуру, версию схемы, SQLite integrity_check и foreign_key_check.
- Неизвестную более новую схему, повреждённую или несовместимую базу не пересоздавать
  и не изменять автоматически; сообщать понятную ошибку.
- Описать отдельную команду создания/проверки базы для разработчика в README.
  Полный пользовательский интерфейс базы не входит в это задание.

## 2. Сущности схемы

Создать сущности, перечисленные в архитектуре:

| Таблица / сущность | Назначение |
| --- | --- |
| imports | Происхождение и статусы загрузок; без чтения выписок на этом этапе |
| operations | Исходные нормализованные банковские факты |
| classifications | Текущее аналитическое решение отдельно от фактов |
| manual_overrides | История ручных решений конкретной операции |
| rules | Постоянный идентификатор и состояние правила |
| rule_versions | Версии формализованных условий и действий |
| operation_link_groups | Группы связанных операций |
| operation_link_members | Участники групп; не ограничиваться парами |
| projects | Проекты и их состояния |
| categories | Справочник категорий с устойчивыми ID и иерархией |
| own_accounts | Подтверждённые собственные счета и доступные идентификаторы |
| audit_log | История существенных изменений |
| schema metadata | Версия структуры базы |

Минимальная банковская запись содержит внутренний ID, import_id, банк,
счёт/карту, operation_date, processing_date при наличии, исходное описание,
сумму, направление IN/OUT, MCC при наличии, контрагента при наличии,
исходный банковский тип, остаток при наличии, позицию и дополнительные
исходные данные, дату импорта. Не добавлять валюту и банковскую категорию.

Денежные значения хранить целыми копейками с проверкой целочисленного типа.
Сумма операции неотрицательна, направление хранится отдельно. Остаток может
быть отрицательным; для него также использовать целые копейки.
Не использовать float для хранения или преобразования денежных сумм.

Защитить обязательные поля, допустимые направления, уникальность версий правила
и ссылочную целостность. Классификация по правилу должна позволять восстановить
точную существующую версию этого правила. Участник группы должен ссылаться на
существующие группу и операцию.

## 3. Минимальные операции доступа и история

Реализовать и проверить создание, чтение и допустимые обновления ключевых
сущностей. Обычное удаление финансовых записей не предоставлять: использовать
состояния, как предписывает архитектура.

- Изменение классификации не перезаписывает банковские факты.
- Новое ручное решение сохраняет предыдущее решение в истории.
- Новая версия правила не изменяет старую версию.
- Существенные изменения справочников и решений фиксируются в audit_log.
- Тестовые данные не записываются в рабочую database/finance.db и не поставляются
  как реальные счета, финансовые категории или пользовательские правила.

Не реализовывать исполнение правил, автоматическое сопоставление операций
или сам исторический финансовый перерасчёт: здесь нужна только поддержка хранения.

## 4. Справочники categories и own_accounts

Реализовать импорт и валидацию пользовательских XLSX-справочников в SQLite,
как требует этап 1 плана. Это импорт справочников, а не банковских выписок.

- Документировать точные колонки и форматы примеров в README или описании схемы.
  Их конкретная файловая разметка не задана исходными документами и является
  техническим решением реализации.
- Подготовить обезличенные шаблоны/примеры в config; не использовать реальные
  ФИО, номера счетов или финансовые категории из истории переписки.
- Проверять обязательные поля, устойчивые ID, дубли, ссылки на родительские
  категории и отсутствие циклов категорий.
- Две категории с одинаковым написанием с разным регистром внутри одного
  родителя не должны случайно превращаться в разные категории.
- Валидировать файл целиком до изменения рабочих данных. Ошибка в строке
  не должна оставлять частично применённый справочник.
- Повторная загрузка того же справочника не создаёт дубли и не удаляет
  отсутствующие в нём старые записи автоматически.
- Обновление существующего ID не должно разрушать ссылки из других таблиц.
- Добавлять только реально используемые зависимости для XLSX и фиксировать версии.

## 5. Версия схемы и миграции

- Реализовать schema_version и последовательный механизм миграций.
- Первая миграция создаёт начальную схему. Проверить её реальное выполнение,
  повторное открытие базы и отказ от повторного применения.
- Изменения схемы выполняются транзакционно, версия меняется только после успеха.
- Проверить откат искусственно неуспешной миграции на временной тестовой базе:
  прежняя версия и данные должны сохраниться.
- До изменения уже существующей базы создавать согласованный backup средствами
  SQLite и проверять его целостность. Ошибка backup блокирует миграцию.
- Полный пользовательский сценарий резервного копирования/восстановления,
  меню backup и политика хранения копий остаются этапу 8.
- Не добавлять фиктивные производственные миграции ради теста; искусственно
  ошибочная миграция может существовать только в тестовом коде.

## 6. Файлы и зависимости

Ориентиры: `program/database/connection.py`, `migrations.py`, `operations.py`,
другие небольшие модули доступа по необходимости, `tests/test_database*.py`,
`tests/test_reference*.py`, `config` с примерами, описание схемы в `docs`,
README и requirements.txt. Использовать встроенный sqlite3; отдельный сервер
баз данных или ORM без обоснованной необходимости не добавлять.

Версию программы хранить в одном месте. Фактический номер новой версии и
список изменений указать в результате реализации; версии программы и схемы
не смешивать. Существующие smoke-тесты сохранять и адаптировать к согласованной
новой версии без ослабления проверок поведения.

## 7. Обязательные проверки

| ID | Что проверяем | Ожидаемый результат |
| --- | --- | --- |
| T1.1 | Создание и повторное открытие | Все таблицы и версия схемы доступны |
| T1.2 | Повторная инициализация | Данные и история сохранены |
| T1.3 | Копейки, направления и обязательные поля | Неверные записи отвергаются, копейки сохраняются точно |
| T1.4 | Изменение аналитики | Исходная operations не меняется |
| T1.5 | Новое ручное решение | Старое решение остаётся в истории |
| T1.6 | Новая версия правила | Старая версия и ссылки на неё сохранены |
| T1.7 | Внешние ключи и группы | Невалидные ссылки отвергаются; группа из трёх участников допустима |
| T1.8 | Валидные XLSX-справочники | Загружаются, повторный импорт не создаёт дублей |
| T1.9 | Ошибочные справочники | Дубли/циклы/битые ссылки дают ошибку без частичного обновления |
| T1.10 | Миграции | Успех, повторный запуск и откат при ошибке проверены |
| T1.11 | Миграция существующей базы | Backup проверен; ошибка backup не меняет исходную базу |
| T1.12 | Неверная/повреждённая/слишком новая база | Понятный отказ, нет автоматического уничтожения или пересоздания |
| T1.13 | Модули и меню | Импорт и показ меню не создают рабочую базу |
| T1.14 | Полный pytest | Старые и новые проверки проходят, без подмены проверок заглушками |
| T1.15 | Windows | Команды установки, создания/проверки базы и pytest выполнены пользователем |
| T1.16 | Git status | Нет рабочей БД, личных справочников, backup, логов или .venv |

Тесты запускаются на отдельных временных базах. Протокол различает проверки
разработчика и проверки, о которых сообщил пользователь. Нельзя заявлять
локальную проверку Windows на основании прогона Linux.
