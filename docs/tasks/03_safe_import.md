# Задание №3 — безопасный накопительный импорт

Статус: реализовано в версии 0.4.0; тесты Linux выполнены, Windows-проверка
ожидается. Протокол: docs/validation_stage3.md.

Основание: этап 3 Плана разработки v1.0; ТЗ v1.1, Архитектура v1.0. Этап 2
принят пользователем на Windows. Рабочий формат остаётся PDF кредитной карты
Сбера, уже выбранный для первого импорта. Остальные банки — этап 4.

## Сделать

- Два уровня повторов: SHA-256 файлов и идентичность банковских операций.
- Предпочитать настоящий банковский ID, когда он доступен; не выдавать код
  авторизации Сбера за уникальный transaction ID.
- При отсутствии ID использовать устойчивые признаки и multiset/occurrence,
  сохраняя реально повторяющиеся одинаковые покупки.
- Перекрывающаяся выписка добавляет только недостающие записи; короткая
  следующая выписка не удаляет старые. Не менять старые ID, факты и решения.
- Сохранять попытки, источник и позицию каждой новой/повторной строки, счётчики
  и ошибки. Не оставлять частично успешный финансовый импорт.
- После успешного импорта переносить источник в проверенный архив по годам/банкам.
  Ошибочный файл не перемещать в архив успешных источников.
- Разделять финансовый COMMIT и состояние архивирования; обеспечить проверяемое
  завершение после сбоя без повторного добавления операций.
- Добавить миграцию и проверенный способ перенести базу версии 0.3.0 в новую
  установку, сохранив исходную базу и backup.
- Сохранить предварительный просмотр, явное подтверждение и понятные результаты.

Технические детали таблиц, идентичностей, архивных состояний и восстановления
описаны в docs/cumulative_import.md. Они не меняют финансовую модель ТЗ.

## Проверки

1. Тот же файл и его переименованная копия: 0 новых операций.
2. Те же строки в PDF с другими байтами: 0 новых по сопоставлению записей.
3. Короткая → полная → расширенная выписка: добавляются только новые вхождения.
4. Две/три реальные одинаковые покупки: все остаются отдельными операциями.
5. Другие даты/счета/банки не объединяются; противоречивый банковский ID отвергается.
6. Сбой парсинга/валидации/SQL откатывает финансовую транзакцию и сохраняет FAILED.
7. Архив проверяется по SHA-256 до удаления исходника; конфликтующий файл
   не перезаписывается, изменённый исходник не удаляется.
8. Сбой после COMMIT и сбой архивирования восстанавливаются без новых операций.
9. Миграция реальной структуры выпущенной версии 0.3.0 сохраняет записи,
   ID, ручные решения и правила; при ошибке возвращается схема 1 и остаётся backup.
10. Весь pytest, проверка реального PDF во временной базе и ручной Windows-прогон.

Подготовить подтверждение A1, A2, A20, A21 для текущего поддерживаемого формата.
Это не финальная приёмка всех банков и всех критериев MVP.

## Не делать

Не подключать остальные банки/форматы, классификацию, поиск финансовых связей,
пользовательские финансовые правила, отчёты, OCR или полный эксплуатационный
интерфейс этапа 8. Не публиковать настоящие выписки или рабочую базу.
