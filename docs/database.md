# База данных: схема 1

Программа 0.2.0, SQLite, только локальное хранение. Данный документ описывает
технические решения реализации этапа 1. Он не изменяет финансовые требования
ТЗ v1.1 и Архитектуры v1.0. Файлы реальных справочников и finance.db не входят в Git.

## Что реализовано

`python -m program.database init` явно создаёт новую пустую базу; повторный запуск
только проверяет существующую. `check` открывает существующий файл для чтения,
не создаёт отсутствующий и проверяет метаданные, таблицы, ограничения, индексы,
защитные триггеры, integrity_check и foreign_key_check. Несовместимые файлы
не исправляются и не пересоздаются автоматически.

Путь по умолчанию: `database/finance.db` относительно корня установленного проекта,
а не текущего рабочего каталога. Для отдельной базы есть `--database ПУТЬ`.
Сам импорт модулей и главное меню базу не создают. В меню финансовые функции
всё ещё остаются заглушками; работа с хранилищем пока доступна через команды
для разработчика и Python API.

Все подключения через `connect()` включают внешние ключи и закрываются по выходу.
`transaction()` начинает BEGIN IMMEDIATE, фиксирует успех и откатывает ошибку.
Вложенные изменяющие транзакции отвергаются, а не фиксируются неожиданно.
Не запускать одновременно миграцию и другие изменяющие операции: режим совместной
работы нескольких пользователей в этом этапе не реализуется.

## Сущности

| Сущность | Ключ и назначение |
| --- | --- |
| schema_metadata | Одна запись singleton=1, schema_version=1 |
| imports | Текстовый id; файл, банк, SHA-256/парсер при наличии, счётчики, PENDING/SUCCESS/FAILED |
| operations | Текстовый id; ссылка на import_id; банковские факты |
| categories | Текстовый id; name, нормализованный name_key, parent_id, ACTIVE/ARCHIVED |
| own_accounts | Текстовый id; bank, account, необязательные owner_name и phone, ACTIVE/ARCHIVED |
| projects | Текстовый id; название, необязательный период, ACTIVE/ARCHIVED |
| rules | Текстовый id; название, ACTIVE/DISABLED; новое правило по умолчанию DISABLED |
| rule_versions | Составной ключ rule_id/version; JSON-объекты условий и действия, приоритет, дата начала |
| classifications | Одна текущая запись на operation_id; тип, учёт, категории/проект, источник решения |
| manual_overrides | Целочисленный id; неизменяемые решения с previous_id для истории операции |
| operation_link_groups | Текстовый id; OWN_TRANSFER/REFUND/CHAIN и статус |
| operation_link_members | Составной ключ group_id/operation_id и явно заданная роль |
| audit_log | Неизменяемая история существенных изменений с before/after в JSON |

Текстовые ID и значения примеров — технический контракт этого этапа. Правила
генерации банковских идентификаторов и дедупликация здесь не определяются.

В operations обязательны id, import_id, bank, account_id, operation_date,
description, amount_kopecks и direction. Дополнительные поля: processing_date,
mcc, counterparty, bank_operation_type, balance_after_kopecks, source_row,
source_data, bank_transaction_id. created_at записывается при создании.
Валюта и банковская категория отсутствуют.

Суммы — целые копейки, direction — IN/OUT. Сумма неотрицательна; остаток может
быть отрицательным. Python API отвергает float, bool и строки вместо целых копеек.
SQL CHECK дополнительно проверяет фактический целочисленный тип хранимого значения.
Даты в API валидируются как календарные ISO YYYY-MM-DD. Сам SQLite не является
универсальным валидатором всех бизнес-правил: запись должна идти через API.

## Сохранение решений и история

`Store` проверяет схему перед работой. Методы создания банковской записи,
смены статуса, ручного решения, версии правила и группы связей пишут audit_log
в одной транзакции с основным изменением.

Банковские записи, версии правил, ручные решения и аудит защищены SQL-триггерами
от UPDATE и DELETE. Остальные финансовые сущности защищены от обычного DELETE;
используются статусы. При ручной корректировке создаётся новое решение, старое
сохраняется и указывается через previous_id. classifications хранит текущее
решение; оно меняется без изменения operations.

Источник классификации — MANUAL, LINK, RULE или UNDEFINED. При RULE обязательна
ссылка на существующий составной ключ версии правила; при MANUAL — на решение
этой операции; при LINK API требует подтверждённую группу с этой операцией.
Автоматическая запись через API не перезаписывает существующую ручную.

Это операции **хранения явно переданных решений**, а не финансовый двигатель.
Правила не исполняются, переводы/возвраты не определяются, итоги не рассчитываются.
Проверки полного финансового состояния и пользовательские сценарии последующих
этапов пока отсутствуют.

## XLSX-справочники

Формат XLSX — техническое решение реализации: ровно один лист, первая строка
с точными заголовками в указанном порядке. Все заполненные ячейки — текст,
включая ID, счета и телефон. Формулы и Excel-ошибки отвергаются. Пустые строки
пропускаются. Необязательное поле оставляется действительно пустым.

**categories:** `id`, `name`, `parent_id`, `status`.

- id, name, status обязательны; parent_id пуст для корневой категории.
- status: ACTIVE или ARCHIVED.
- Родитель может стоять ниже ребёнка в файле, но должен существовать в файле
  или уже в базе. Циклы и повторные ID запрещены.
- Имена сравниваются внутри одного родителя после strip, Unicode NFKC и casefold.
  Это предотвращает дубли кириллических названий с разным регистром.
- Импорт проверяет объединение файла и сохранённых категорий. Перенос подкатегории
  не должен нарушать ни текущие, ни исторические ручные решения.

**own_accounts:** `id`, `bank`, `account`, `owner_name`, `phone`, `status`.

- id, bank, account, status обязательны; owner_name и phone необязательны.
- status: ACTIVE или ARCHIVED. Пара bank/account уникальна.
- Никакой автоматической проверки принадлежности счёта банком не выполняется.

В `config/*.template.xlsx` лежат **пустые** шаблоны только с заголовками.
Скопировать их в `config/categories.xlsx` и `config/own_accounts.xlsx` можно
позже, когда понадобятся собственные справочники. Последние пути исключены из Git.
Рабочая база изначально не содержит категорий, счетов, правил или проектов.

Импорт сначала читает и проверяет файл, затем проверяет его вместе с текущей
базой под транзакцией и выполняет upsert по устойчивому ID. Отсутствующие в
новом файле записи не удаляются и не архивируются. Повтор без изменений даёт 0
изменений и не создаёт повторный аудит. Любая ошибка откатывает все изменения
и аудит текущего импорта. Перед изменением уже существующих записей создаётся
и проверяется SQLite-backup; ошибка backup блокирует изменение. Повтор без
изменений и добавление новых записей не создают лишние копии. Для базы по
умолчанию копия попадает в backup/ корня проекта, для отдельной базы — в backup/
рядом с ней. Полное пользовательское меню резервного копирования остаётся этапу 8.

## Миграции

Реестр содержит единственную производственную миграцию: создание схемы 1.
Никаких будущих фиктивных схем ради теста в программу не добавлено.
Функция migrate принимает последовательность Migration(version, apply, validate).
Перед изменением существующей совместимой базы она создаёт новый файл backup
через SQLite backup API и проверяет его исходным валидатором. Неудачный backup
блокирует миграцию. Все шаги изменения схемы и метаданных выполняются одной
транзакцией; ошибка возвращает прежние таблицы, значения и версию.

Поддержка миграций последующих версий предполагает добавление их к реестру
и соответствующих валидаторов. Текущая программа не понижает версию более новой
базы и не пытается автоматически исправить повреждённый файл.

Пользовательское меню backup, восстановление, политика хранения копий и полноценная
эксплуатационная самопроверка остаются этапу 8. Критерии A18/A19/A22 на этапе 1
подготовлены структурой хранилища, но не объявляются полностью закрытыми.
